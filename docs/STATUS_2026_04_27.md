# Daily Status — 27 April 2026

**Branch:** `feature-power-snmp-detection`

---

## What We Did Today

The pipeline was already running end to end, but when we checked the numbers the
detection quality was not good enough for production.  Recall (how many real faults
we actually catch) was only **44.5%** — meaning we were missing more than half of all
anomaly events.  Today we diagnosed why and fixed it.

---

### Problem: What Was Being Missed

After running a full evaluation we found four specific blind spots:

- **Environment sensors** (`env_gen_01`) — we were catching **zero** anomalies despite
  892 true events.  The global detection threshold was set by UPS devices, which have
  much higher reconstruction error, so environment device faults looked completely normal.

- **Overload events** — only 8% recall.  The LSTM could not see overload coming fast
  enough because we were only giving it a 50-minute window, and the faults ramped gradually.

- **Thermal runaway** — 38% recall.  Same problem: gradual temperature rise over many
  steps looks unremarkable in a short window.

- **Phase voltage sag** — 21% recall.  Small voltage dips were falling just below the
  detection threshold.

---

### Fix 1 — Added Two New Features

We added `temperature_delta` and `output_load_delta` to every preprocessing run.
These measure *how fast* temperature and load are changing step to step, not just what
the current reading is.  A thermal runaway has a steadily rising delta even before
absolute temperature looks alarming.

**Result:** thermal runaway recall jumped from 38% → **95%**.

---

### Fix 2 — Doubled the Context Window

The LSTM now looks at 20 time steps instead of 10 (100 minutes of history instead of 50).
Gradual faults accumulate enough reconstruction error across the longer window to be noticed.

---

### Fix 3 — Tightened the Detection Threshold

We lowered the threshold multiplier from 3.0× to 2.0× standard deviation.
Our false positive rate was only 0.4% before — there was plenty of room to tighten without
causing spurious alerts.

---

### Fix 4 — Per-Device-Category Thresholds

Instead of one global threshold calibrated on UPS data, each device category now gets
its own threshold calculated from its own normal error range:

| Device Type | Threshold |
|---|---|
| UPS | 0.219 |
| PDU | 0.113 |
| Network | 0.172 |
| Environment | 0.112 |

Environment sensors get a much tighter threshold (0.112 vs. global 0.193) — this is why
`env_gen_01` went from **0 detections to 881 correct detections**.

---

### Fix 5 — Rule-Based Overload Detection

`output_load_pct > 100` is physically impossible during normal operation (load cannot
exceed 100% in our data model).  We added a simple rule: any window containing a reading
above 100% is flagged regardless of what the model says.  Zero false positives from this
rule because it can never fire on real normal data.

---

### Retrained Both Models

With all five fixes in place, both the baseline LSTM and the phase-level LSTM were
retrained from scratch on the updated feature set.

```
Baseline: 30 epochs  →  final loss 0.112847  →  threshold 0.193343
Phase:    30 epochs  →  final loss 0.077053  →  threshold 0.131329
```

## Full Pipeline (Working Right Now)

```bash
# 1. Generate training data
python3 -m snmp_anomaly_detection generate-power-data

# 2. Train models
python3 -m snmp_anomaly_detection train-power-baseline
python3 -m snmp_anomaly_detection train-power-phase
python3 -m snmp_anomaly_detection train-battery-rul

# 3. Run detection
python3 -m snmp_anomaly_detection detect-power-csv

# 4. Live Kafka stream
python3 -m snmp_anomaly_detection detect-power-kafka
```

Outputs land in `snmp_anomaly_detection/outputs/power_dual/`:
- `anomaly_results.csv` — every scored window with final_flag column
- `detection_summary.json` — breakdown by device, vendor, and category
- `anomaly_windows_detail.json` — per-timestep attribution for each flagged window

## What's Still Not Good Enough

Three gaps remain after today's fixes:

| Issue | Current Recall | Why It's Hard |
|---|---|---|
| Moderate overload | 65% | Normal load variance overlaps the 65–100% range; rule only fires above 100% |
| Phase voltage sag | 54% | Small L1/L2/L3 dips still sit below the phase model threshold |
| Liebert 3-phase UPS | 73% | Voltage imbalance features are near-zero during many fault types on this device |

## What We Plan to Do Next

**Short term (next 1–2 sessions):**

1. **Improve overload recall** — add a soft overload rule that fires at load > 90% sustained
   over multiple steps, rather than waiting for the hard > 100% violation.

2. **Improve phase sag recall** — lower the phase model threshold specifically for voltage
   features (per-feature thresholds, not just per-category), or add a dedicated delta feature
   for per-phase voltage drop.

3. **Fix Liebert 3-phase gaps** — investigate whether imbalance enrichment is computing
   correctly for the Liebert OID mapping and add a separate fault type label if needed.

**Medium term:**

4. **Connect to real SNMP data** — replace the synthetic dataset with live SNMP poll data
   once the collection setup is ready.  The vendor OID mapping (`vendor_oid_map.py`) and
   canonical feature names (`config.py`) are already in place for this.

5. **ClickHouse integration** — replace the `.csv` / `.jsonl` output files with columnar
   storage in ClickHouse so Grafana can query detection results directly.

6. **Grafana dashboards** — anomaly rate per device/category, RUL forecast timelines,
   compound alert history.
